# CRM page.tsx 탭 분리 — 설계 메모 (2026-11-23)

사장님 지시: **"탭 하나씩 분리한다고 해서 기능이 꼬이면 곤란해. 처음부터 체계적으로 잘 분리해보자."**

## 2. 탭끼리 공유하는 것 (꼬이면 안 되는 흐름)

| 흐름 | 시작 | 거치는 것 | 끝 |
|---|---|---|---|
| 예약 완료 → 시공 기록·사후관리 생성 | 예약/일정 "작업 내역서 → 시공 완료 처리", 홈 "완료 처리" (`handleStatusChange` → `handleOpenWorkOrder`) | `doWorkOrderSubmit`: services insert → `createAutoFollowUps` → 회원 링크 문자 → 소개 포인트 → `fetchAppointments`+`fetchFollowUps` | 홈 카드·예약/일정·사후관리 셋 다 갱신 |
| QC·메인터넌스 방문 잡기 | 사후관리 카드 "📅 방문 잡기" (`openCareBook` → 창 `careBook`) | `handleBookCareVisit`: appointments insert(follow_up_id) + 사후관리 날짜 변경 | 예약/일정 달력에 방문 예약, 손님 페이지 '다음 관리' |
| 달력의 방문 예약 완료 → 사후관리 완료 | 예약/일정 "점검 완료" (`handleOpenCareVisit`) 또는 상태 변경→완료 | `careVisitAppt`+`careTarget` → CareCompleteModal → `handleCareDone`(다음 메인터넌스 자동) | 예약도 완료, 사후관리 완료, 홈 카드 갱신 |
| 홈 카드가 읽는 것 | — | `appointments`·`followUps`·`allCustomers`·`teamBrief`·`stats` | 홈은 **읽기만** 하고 쓰는 핸들러는 `handleStatusChange`·`openDateEdit`·`handleTeamSms` 셋 |

## 3. 구조 결정 — "목록 상태·로더는 훅, 탭 화면은 props, 핸들러·창 상태는 page.tsx"

- **훅 `src/hooks/useCrmData.ts`**: 표 A 에서 "쓰는 곳"이 자기 fetch 함수뿐인 상태(`customers`·`appointments`·`followUps`·`consultations`·`allCustomers`·`vehiclesByCustomer`·`teamBrief`·`stats`)와 fetch 7개, 탭 바뀔 때 읽는 effect 를 그대로 옮겼다. 이들은 supabase 와 자기 setter 만 보므로 떼어도 호출 시점이 바뀌지 않는다. `teamOpen`·`statsMonth`·`statsDays` 는 fetch 함수가 setter 를 쓰거나 effect 가 읽어서 같이 갔다.
- **탭 화면은 컴포넌트 + props**: 표 B 를 보면 핸들러 대부분이 창 상태(`workOrderAppointment`·`careTarget`…)와 여러 탭이 같이 쓴다(`handleStatusChange`·`openDateEdit` 는 홈+예약/일정, `handleAddCustomerFromQuote` 는 사후관리+상담). 핸들러를 탭 안으로 옮기면 같은 로직이 둘로 갈라지거나 창 상태까지 끌려가므로, 이번 단계에서는 page.tsx 에 두고 **함수 그대로 props 로** 내렸다.
- **탭 UI 상태(검색어·달력 월·선택 날짜·필터·접힘)도 page.tsx 에 둔다**: 탭은 `{activeTab === 'x' && <XTab/>}` 로 조건부 렌더라 탭을 오가면 언마운트된다. 상태를 탭 안에 두면 다른 탭 갔다 오는 순간 검색어·선택 날짜가 지워져 지금 동작과 달라진다. "동작 변경 없음"을 지키려고 전부 props 로 유지했다. 대신 props 가 많아졌다(홈 23·사후관리 24·예약/일정 26).
- **IIFE 탭**(홈·예약/일정)은 `(() => { 계산; return (...); })()` 본문을 그대로 컴포넌트 본문으로, **일반 탭**은 JSX 를 `return (...)` 으로 감쌌다. 들여쓰기만 바뀌고 글자는 같다(6절).
- `today` 는 page.tsx 에서 한 번 `todaySeoul()` 로 계산해 내려준다(원본과 같은 자리).
- 둘러보기 `isDemo` 분기는 홈·예약/일정에 그대로 props 로.

## 4. 진행 순서와 이유

실제 순서: 훅(2be503d) → 홈(575ed9a) → 상담 기록(6f01826) → 사후관리(347dfdf) → 고객 목록(c46a66f) → 예약/일정(85692ea). 시작 세션이 준 순서를 그대로 따랐다.
표로 보면 의존이 가장 적은 탭은 상담 기록(props 6)·고객 목록(10)이고 홈(23)·사후관리(24)·예약/일정(26)이 많다. **홈을 먼저 해도 괜찮았던 이유**는 홈이 공유 상태를 많이 *읽기만* 하고 쓰는 핸들러가 셋뿐이라 옮겨도 다른 탭의 흐름을 건드리지 않기 때문이다. 의존도 기준으로 다시 정한다면 상담 기록 → 고객 목록 → 홈 → 예약/일정 → 사후관리 순이 맞고, 2단계(창·핸들러)에서는 이 기준을 쓴다.
탭마다 `npx tsc --noEmit` → `npm test`(vitest 38) → `npm run build` 를 통과한 뒤에만 커밋했고, 깨진 단계는 없었다(한 번 줄 번호 확인이 어긋나 스크립트가 아무 것도 바꾸지 않고 멈춘 것을 고쳐 다시 돌린 것뿐).

## 7. 남은 위험

1. **props 가 많다**(최대 26). 탭에 새 버튼을 넣으면 page.tsx(핸들러·props 전달)와 탭 파일(props 타입·JSX) 두 군데를 고쳐야 한다. 빠뜨리면 tsc 가 잡는다.
2. **`Window.Kakao` 전역 타입이 page.tsx 의 `declare global` 에 있다.** FollowUpsTab 의 카톡 보내기가 이 타입에 기댄다. tsc 는 프로젝트 전체를 보므로 지금은 통과하지만, page.tsx 에서 그 선언을 지우거나 page.tsx 를 더 쪼갤 때 `src/types/kakao.d.ts` 같은 파일로 먼저 옮겨야 한다.
3. `CustomerPicker` 가 page.tsx 안에서 매 렌더마다 새로 정의되는 컴포넌트다(원래부터 그랬음, 그대로 둠). 2단계에서 예약 추가·상담 추가 창을 컴포넌트로 뗄 때 같이 `src/components/crm/CustomerPicker.tsx` 로.
4. 옮긴 JSX 안의 기존 eslint 오류(따옴표 이스케이프, `<img>`)는 그대로다. `next build` 는 eslint 를 돌리지 않아 빌드에 영향 없음. 고치려면 별도 커밋으로.
5. 사후관리 탭의 `followUpFilter` 타입은 page.tsx 에 인라인 유니온, 탭 파일에 `FollowUpFilter` 로 중복 선언돼 있다(구조적으로 같아 통과). 한쪽에 값을 추가하면 다른 쪽도.
6. **800줄 목표 미달.** 2단계 제안: ① 인라인 창 6개를 `src/components/crm/` 컴포넌트로(저위험, 약 -300줄) ② 핸들러를 흐름별 훅으로 — `useWorkOrderFlow`(작업 내역서 열기·저장·완료·보증서), `useCareFlow`(점검 기록·리터치·방문 예약·완료 토글), `useCustomerActions`(등록·수정·삭제·견적에서 등록), `useAppointmentActions`(추가·삭제·상태·날짜·스크린샷). 핸들러는 서로를 부르고(`handleStatusChange` → `handleOpenWorkOrder`/`handleOpenRetouch`/`handleOpenCareVisit`) 창 상태를 공유하므로 2단계는 **이 메모의 표 B 를 먼저 갱신해 훅 경계를 그린 뒤** 한 훅씩, 같은 검증(tsc·test·build·원본 대조·화면)으로 간다.
